TÍTULO: Análisis de proceso actual por tipo de pregunta y evaluación de mejoras
═══════════════════════════════════════════════════════════════════════════════

DESCRIPCIÓN GENERAL
───────────────────
Analizar cada tipo de pregunta que maneja PIBot y documentar en un archivo HTML
de una sola página: (1) qué hace el clasificador, (2) qué reglas de negocio
aplica post_classifier.py, (3) qué instrucciones concretas se inyectan al LLM
en response.py, y (4) posibles mejoras para reducir o eliminar las reglas de
negocio delegando más responsabilidad al clasificador.

OBJETIVO
────────
La meta de largo plazo es eliminar los árboles de decisión de post_classifier.py
de modo que las respuestas sean lo más transparentes posibles al clasificador.
Antes de hacerlo se necesita un mapa completo del estado actual por tipo de
consulta.

───────────────────────────────────────────────────────────────────────────────
ARQUITECTURA ACTUAL (contexto relevante para el agente)
───────────────────────────────────────────────────────────────────────────────

1. CLASIFICADOR
   - Primer clasificador (intent): decide si la consulta es metodología o datos.
     Endpoint: PREDICT_URL = http://localhost:8000/predict
   - Segundo clasificador (intents + entities): entrega calc_mode, activity_cls,
     indicator, frequency, period, seasonality, region, investment, etc.
     Endpoint: INTENT_CLASSIFIER_URL = http://localhost:8100/intent
   - NER normaliza entidades (indicator_ent, activity_ent, period_ent, etc.)

2. POST-CLASIFICACIÓN
   - Archivo: rules/post_classifier.py
   - Clase principal: BusinessRuleEngine con métodos apply_business_rules()
   - Reglas numeradas Rule01…Rule14 (aprox). Cada regla muta ResolvedEntities.
   - Algunas reglas corrigen falencias del clasificador; otras son lógica de
     dominio irremplazable.

3. RESPONSE
   - Archivo: orchestrator/data/response.py
   - Función principal: build_messages(question, entities_ctx, observations, ...)
   - Construye la lista de mensajes de sistema enviados al LLM.
   - Funciones clave: _build_metric_priority_instruction(calc_mode),
     _build_economy_wording_instruction(), _build_annual_pib_completeness_instruction(),
     _build_no_explicit_period_latest_instruction(),
     _build_historical_pib_yoy_instruction(), _build_original_series_force_instruction(),
     _build_value_no_rescale_instruction(), _build_recommendation_length_instruction(),
     _build_specific_contribution_directness_instruction(),
     _build_missing_activity_instruction(), _build_share_instruction(), etc.

ESTRUCTURA GENERAL DEL HTML
────────────────────────────
- DOCTYPE html, lang="es", charset UTF-8
- <header> azul oscuro (#003566) con título h1 y línea de metadata (fecha, rama, archivos)
- <main> max-width 1560px con:
    1. .arch-box   → leyenda de colores de código (1 sola, al inicio)
    2. N × .card   → una por tipo de consulta (TIPO 0 a TIPO 14)
    3. .summary-section → tabla resumen al final (opcional, si hay tiempo)

ESTRUCTURA DE CADA .card
─────────────────────────
<div class="card">
  <div class="card-header cN">          ← N = número del tipo (0-14)
    <span class="badge">TIPO N</span>
    <h2>Nombre del Tipo</h2>
  </div>
  <div class="card-body">
    <table>
      <tr><th>PU — Ejemplos</th><td><ul class="pu-list"> ... </ul></td></tr>
      <tr><th>PREDICT_URL outputs</th><td> ... </td></tr>
      <tr class="sep-rule"><th>Regla post_classifier</th><td>
        [ pill verde/rojo/azul ] + pseudo-código si aplica
      </td></tr>
      <tr><th>Instrucción LLM<br/>(response.py)</th><td>
        bloque .llm-wrap con pseudo-código de disparador +
        <details class="instr-expand"> con texto literal completo
      </td></tr>
      <tr><th>Solución propuesta</th><td>
        .bug-box (fondo rojo) para bugs y/o .mejora-box (fondo verde) para mejoras
      </td></tr>
      <tr><th>calc_mode / Freq.</th><td> pills con valores finales </td></tr>
      <tr><th>Clasificación real (log)</th><td>
        .json-outer + .json-block con JSON real del clasificador (o .obs-box si sin log)
      </td></tr>
      <tr><th>Eliminable</th><td> pill con clasificación </td></tr>
    </table>
  </div>
</div>

CSS — CLASES PRINCIPALES (copiar del archivo de referencia)

Bloques de pseudo-código (reglas de negocio):
  .pseudo-wrap / .pseudo-label / .pseudo-code
  Syntax highlighting:
    .kw   → pink  (#f472b6)  — IF / THEN / AND / OR
    .cond → blue  (#93c5fd)  — condiciones / valores del clasificador
    .act  → green (#4ade80)  — mutaciones de entidades

    .bug  → red   (#f87171)  — marcador de bug
    .cm   → gray  (#475569)  — comentarios

  .llm-wrap / .llm-label / .llm-code
  Syntax highlighting:
    .fn   → indigo (#a5b4fc) — nombre de función
    .cond → violet (#c4b5fd) — condición
    .inj  → teal   (#6ee7b7) — texto inyectado
    .cm   → darkgray (#4c4b7a) — comentario

Bloques de texto literal (colapsable):
  <details class="instr-expand">
    <summary></summary>   ← vacío; el texto lo pone ::before CSS
    <div class="instr-literal">
      Texto literal copiado verbatim de response.py.
      Envolver con spans:
        <span class="R"> nombre de la regla / sección (color amber #fde68a) </span>
        <span class="P"> PROHIBIDO (color red #fca5a5) </span>
        <span class="O"> OBLIGATORIO (color teal #6ee7b7) </span>
    </div>
  </details>

  CSS clave para el acordeón:
    details.instr-expand > summary::before { content: "▶ ver texto literal enviado al LLM"; }
    details.instr-expand[open] > summary::before { content: "▼ ocultar texto literal"; }
    .instr-literal { background: #1c1a3e; border-left: 3px solid #6366f1; ... }

Bloques de log JSON:
  .json-outer / .json-label / .json-block
  Syntax highlighting: .k (key), .s (string), .n (number), .warn (rojo), .ok (verde)

Pills de estado:
  .pill-green  → SÍ aplica / correcto
  .pill-red    → NO aplica / error
  .pill-blue   → regla activa
  .pill-yellow → mejora parcial
  .pill-gray   → N/A
  .pill-purple → caso especial

Cajas de observaciones:
  .bug-box    → fondo rojo   — bugs en reglas actuales
